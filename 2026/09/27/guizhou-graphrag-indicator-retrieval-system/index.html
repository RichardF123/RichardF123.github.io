贵州统计指标 GraphRAG：从自然语言问题到可解释的混合检索系统

这篇文章复盘我的 Guizhou-GraphRAG 项目。它面向贵州统计指标检索场景：用户不需要记住正式指标名称，只要用自然语言描述“想分析什么”，系统就会在已有指标库中召回最相关的指标，并返回定义、类别、匹配原因与图谱路径。

它并不是一个让大模型自由生成答案的聊天机器人。项目真正要解决的问题是：如何把口语化、带方言和不完整条件的问题，可靠地映射到一组真实存在、口径明确的结构化统计指标。

1. 为什么要做“指标检索”，而不是普通问答

统计分析的第一步通常不是立刻计算，而是先回答：应该用哪些指标？

例如，用户问：

正式指标库里未必存在这句原话，可能只有“留守老人数量”或相近的规范名称。用户还可能把“马铃薯”说成“洋芋”，把“公共厕所”说成“公厕”，或者在语音输入中把“马铃薯”识别为“马玲薯”。

如果只做字符串匹配，系统会漏掉口语和同义表达；如果只做向量检索，又可能因为语义接近而把父指标、子指标和同类指标混在一起。更麻烦的是，统计指标中存在大量“数量、面积、是否、情况”这样的通用词，仅凭这些词相同并不能证明两个指标相关。

因此，这个任务需要同时满足四个目标：

  1. 高召回：口语、简称、方言和不完整问题也能找到候选指标。
  2. 高精度：完整名称、对象、属性与限定条件必须被尊重。
  3. 可解释：用户要知道为什么匹配，以及指标采用什么统计口径。
  4. 可约束：模型只能选择真实指标，不能凭空创造一个听起来合理的名称。

这正是知识图谱与混合检索适合介入的地方。

3. 从原始指标到结构化语义

每条指标不能只保存一个名称。系统会把原始文本解析为更细的语义字段：

其中最关键的拆分是：

  • Object：统计对象，例如人口、老人、耕地、生活垃圾。
  • Property：统计属性，例如数量、面积、类型、是否分类。
  • Condition：限定条件，例如常住、户籍、当年、公共、无人照顾。
  • ValueType：结果类型，例如 count、area、boolean。

为什么要拆这么细？因为“垃圾数量”和“垃圾是否分类”共享对象，却不是同一个问题；“常住人口”和“户籍人口”共享属性，却有不同统计条件。把指标拆成语义骨架以后，排序器才能判断候选究竟是“真的匹配”，还是只碰巧包含几个相同词。

项目当前的前端演示资产包含 2098 条指标，覆盖 26 个类别。正式部署时，授权指标数据、Embedding 缓存和图谱运行产物应由后端在运行时挂载，不应把密钥、内网地址或受限数据写入前端和代码仓库。

Property 统计属性

图谱的作用不是把所有指标连接成一张越大越好的网，而是提供受控扩展。系统只沿父子、别名、同对象、同属性和类别关系扩展候选。如果扩展过宽，GraphRAG 反而会把大量弱相关节点带入结果。

例如，精确命中“马铃薯”以后，图谱可以补充“鲜薯产量”等子指标；但这些扩展结果不能越过完整名称的精确命中。图结构提供召回证据，保护规则决定最终秩序。

5. 查询规范化：方言、错字与语音识别

这个项目很有地方场景特色的一层，是保守的查询规范化。

系统先从指标名、别名和农村口语词典建立候选词表，再组合几类信号：

  • 精确别名：洋芋 -> 马铃薯。
  • 拼音一致：处理同音字和语音识别结果。
  • 形近字：马玲薯 -> 马铃薯。
  • 字符顺序：处理少量顺序错乱。
  • 模糊相似度：使用 RapidFuzz 生成候选。

但纠错不是“看到相似词就强行替换”。候选必须映射到指标库中已经存在的正式名称或别名，并满足置信度阈值。低置信别名只参与候选召回，不自动改写原问题。

6. Local、Global 与跨类别路由

用户问题并不都在问同一层级。项目将查询分成三类：

路由 示例 检索目标
local 村里没人照顾的老人有多少 找到具体指标，优化 Top-1
global 农田水利有哪些指标 找到相关类别与类别内代表指标
cross_category 产业发展和集体经济有哪些指标 覆盖多个相关类别

local 查询主要在指标实体层检索；global 查询会优先对类别社区进行排序；跨类别查询则合并多个社区结果。这比把所有问题都丢进同一个向量索引更合理，因为“找一个指标”和“介绍一个指标体系”本来就是不同任务。

每个类别社区保存类别名称、指标数量、代表指标和摘要。GraphRAG 在这里不仅是“图上的向量搜索”，还承担了从实体级检索切换到社区级检索的作用。

7. 混合召回为什么比单路检索更稳

第一阶段会并行收集多路候选：

  1. 指标名称精确匹配。
  2. 别名和同义词匹配。
  3. 字面相似与关键词覆盖。
  4. Embedding 语义召回。
  5. 父子、同对象和同属性图谱扩展。
  6. 类别路由与查询规划召回。

不同召回器解决的是不同失败模式：

  • 精确匹配精度高，但无法理解口语。
  • 关键词检索可解释，但不擅长语义改写。
  • Embedding 能发现语义相似，却容易混淆相邻概念。
  • 图谱能补充结构关系，但扩展过多会引入噪声。

混合检索的关键不是简单把结果拼起来，而是让多种证据进入统一评分，并在排序前做相关性门控。系统的基础思想可以写成：

8. 三条精度保护规则

8.1 原词优先

同义词可以互相召回，但用户输入的完整原词应当优先：

8.2 通用属性不能单独证明相关

“数量、面积、是否、情况”在指标库中出现频率很高。候选只有同时满足对象、属性、条件、别名或定义等多项证据，才能获得高分。

8.3 宽泛指标降权

像“基本情况”“人口情况”“数量”这样的宽泛指标很容易与许多问题产生弱匹配。系统会施加惩罚，避免它们长期占据前排。

这些规则体现了搜索系统中的一个重要经验：召回模型负责尽量不漏，排序和保护规则负责不要胡来。

9. LLM、Bi-Encoder 与 Cross-Encoder 各做什么

LLM 在当前系统中主要有两个可选职责：

  1. 从问题中提取对象、属性、条件、意图、类别和候选短语。
  2. 在候选集合内给出重排与匹配解释。

它不能创造候选集合以外的指标。这样即使模型产生幻觉，也无法把不存在的名称混入最终结果。

向量召回通常使用 Bi-Encoder：问题和指标卡片分别编码，适合从大量指标中快速取 Top-K。Cross-Encoder 则把 query + candidate 一起输入模型，逐对判断相关性，精度潜力更高，但计算成本也更高。因此合理的两阶段流程是：

11. 如何评价一个指标检索系统

仅仅展示几个成功案例不够，检索系统必须有固定测试集和量化指标。项目使用以下指标：

当前 100 条测试基线为：

指标 结果
Top-1 命中率 89.58%
Recall@5 100%
MRR@5 94.44%
类别召回率 96.15%

这组结果说明第一阶段召回已经比较完整，因为 Recall@5 达到 100%；下一步优化重点应放在前五名内部的顺序，也就是提升 Top-1 与 MRR，而不是继续无边界地扩张候选集合。

同时要保留专门的回归样例，例如“马”“马铃薯”“土豆”“留守老人”和“生活垃圾是否分类”。一个新模型即使总体分数更高，只要破坏这些关键边界，也不应直接替换当前链路。

12. 部署与安全边界

公开前端可以部署在 GitHub Pages，但 Python API、授权指标文件和模型服务应部署在受控服务器。生产环境需要遵守以下边界：

  • 指标文件通过 INDICATOR_PATH 在运行时挂载。
  • 图谱、三元组和 Embedding 缓存写入独立运行目录。
  • LLM、Embedding 和 Reranker 的地址与密钥使用环境变量注入。
  • 浏览器只访问自己的后端代理，不直接保存长期有效密钥。
  • 外部网页资料只能作为补充来源，必须保留 URL、时间和可信度说明。
  • 模型生成的解释、授权指标与公开补充资料需要明确区分。

这种设计让代码可以公开展示，同时把真正需要保护的数据和凭据留在部署环境中。

13. 这个项目让我学到什么

这个项目最重要的收获，不是“会调用一个 GraphRAG 库”，而是开始用搜索系统的方式思考 LLM 应用：

  1. 先定义真实任务。 这里的目标不是生成一段流畅回答，而是从指标库中找到正确实体。
  2. 把召回和排序分开。 第一阶段尽量不漏，第二阶段再解决精确顺序。
  3. 让模型处在约束中。 LLM 可以理解和解释，但最终实体必须来自受控集合。
  4. 结构化信息仍然重要。 对象、属性、条件和父子关系是单纯向量相似度无法稳定替代的。
  5. 评估决定是否上线。 新增 Reranker、别名或图谱边，必须经过同口径测试，而不是凭几次人工体验判断。

从作品集角度看，它把 NLP、信息检索、知识图谱、RAG、后端 API、前端交互、语音输入和离线评估连成了一个完整闭环。它也比“上传 PDF 然后问答”的基础 RAG 更接近真实业务：数据有权限边界，实体有严格口径，查询有地方语言差异，结果还必须可解释和可回归测试。

14. 下一步改进方向

接下来可以沿四条路线继续打磨：

  • 检索评估：扩充困难负样本，按短词、别名、父子指标、跨类别问题分别统计结果。
  • 学习排序：使用人工标注或点击反馈训练轻量 Learning-to-Rank 模型，减少手工权重依赖。
  • 图谱存储：数据规模扩大后，将离线 NetworkX 图迁移到更适合持久化查询的图数据库或关系存储。
  • Agent 报告：在本地指标不足时，检索贵州省统计局、统计年鉴和统计公报等公开来源，并对口径差异做明确提示。
